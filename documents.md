# Требования к документации

Этот файл задаёт обязательные правила для пользовательской документации проекта. Применяйте их при изменении интерфейса, поведения программы, форматов файлов, настроек, `README.md`, `docs.md` или PDF-копии руководства.

## Файлы и их назначение

- `docs.md` — полное руководство пользователя и основной источник текста документации.
- `output/pdf/docs.pdf` — PDF-копия `docs.md` для выпущенной версии. Между выпусками она может отставать от `docs.md`.
- `README.md` — краткое описание проекта, ссылка на полное руководство и актуальная структура репозитория.
- `documents.md` — требования к подготовке, проверке и выпуску документации.

Не дублируйте полное руководство в README. README помогает понять назначение проекта, запустить его и перейти к подробной документации.

## Когда обновлять документацию

Обновляйте документацию в той же задаче, если меняются:

- видимые вкладки, панели, окна, кнопки или подписи;
- доступность элементов и условия их появления;
- порядок действий пользователя;
- значения по умолчанию, диапазоны, единицы измерения или правила проверки;
- расчёты и показатели, которые видит пользователь;
- графики, интерактивные инструменты и сценарии;
- импорт, экспорт, создаваемые файлы или сохраняемые настройки;
- состав Python-файлов проекта: добавление, удаление или переименование файла требует обновить структуру в README;
- версия приложения или поддерживаемая среда запуска.

Внутренний рефакторинг без изменения пользовательского поведения не требует правки руководства.

## Содержание полного руководства

`docs.md` должен описывать текущую версию приложения целиком:

- каждую вкладку, панель и диалоговое окно;
- каждую кнопку, ссылку, команду, клавишу и интерактивное действие;
- каждое поле, флажок, переключатель, список, таблицу, карточку и строку состояния;
- назначение элемента, результат действия и побочные эффекты;
- условия доступности, блокировки, появления и скрытия элемента;
- допустимые значения, единицы измерения, значения по умолчанию и сообщения об ошибках;
- работу графиков, легенды, подсказок, масштабирования и выбора кривых;
- форматы импорта и экспорта, имена создаваемых файлов и сохраняемые настройки;
- ограничения модели, учебное назначение и предупреждения об использовании результатов.

Берите факты из текущего кода, встроенных данных и проверенного поведения программы. Не описывайте предполагаемые функции и не восстанавливайте поведение по памяти. Названия элементов интерфейса приводите точно, включая регистр, кавычки, обозначения и единицы измерения.

## Структура `docs.md`

В начале руководства должны находиться:

1. название документа;
2. версия приложения;
3. краткое описание и предупреждение об ограничениях;
4. содержание с рабочими гиперссылками на все основные разделы.

Дальше расположите быстрый старт, описание главного окна и разделы в порядке, близком к интерфейсу. Для крупных разделов добавляйте ссылку возврата к содержанию. Термины, формулы, файлы, проверку данных и сохранение настроек выносите в отдельные разделы, если они нужны для понимания программы.

## Таблицы

Используйте таблицы для повторяющихся пар «элемент — назначение» и похожих справочных данных.

- Первый столбец хранит заголовки, названия элементов, команд, функций и окон.
- Текст первого столбца должен помещаться в одну строку в PDF.
- Не добавляйте в первый столбец ручные переносы строк.
- Подбирайте ширину первого столбца по самому длинному названию, сохраняя место для понятного описания во втором столбце.
- Все строки одной таблицы должны содержать одинаковое число столбцов.
- Название элемента и описание не должны повторять друг друга без новой информации.

Если название не помещается, сначала расширьте столбец или сократите формулировку без изменения точной подписи интерфейса. Уменьшайте шрифт только тогда, когда это не ухудшает читаемость.

## Язык и редактура

Пишите по-русски в нейтральном профессиональном стиле. Используйте короткие предложения, активный залог и конкретные глаголы. Объясняйте термин при первом упоминании, если он может быть незнаком пользователю.

В обычной задаче проверяйте изменённые фрагменты через `ru-text:ru-check` ([ru-text](https://github.com/talkstream/ru-text)). Перед выпуском версии прогоните документ целиком. Для выпуска проверка только изменённых фрагментов не считается полной. Инструмент возвращает замечания и не меняет файл. Внесите исправления отдельно, затем повторите проверку.

При вычитке проверяйте:

- кавычки-ёлочки для названий интерфейса и отсутствие удвоенных или лишних кавычек;
- отсутствие повторов слов, двойных пробелов, лишних стрелок и случайных символов;
- правильные тире, дефисы, минусы, диапазоны и многоточия;
- неразрывные пробелы после односимвольных русских предлогов и союзов в обычном тексте;
- согласование, управление, однородность списков, тавтологии и канцелярит;
- единообразие терминов, обозначений, единиц измерения и подписей;
- сохранность технических литералов, имён файлов, команд, формул и примеров ввода.

Не заменяйте точку на запятую внутри примеров числового ввода, если интерфейс требует точку. Не меняйте текст интерфейса ради редакторской нормы: сначала исправьте подпись в программе, затем синхронно обновите документацию.

## Требования к README

- Ссылка на `docs.md` должна находиться в начале README, до подробного описания проекта.
- README должен содержать актуальную версию, команды запуска, проверки и сборки.
- Раздел «Структура проекта» должен перечислять каждый отслеживаемый файл `.py` и кратко объяснять его назначение.
- Полноту списка Python-файлов проверяйте по выводу `git ls-files '*.py'`.
- README должен оставаться кратким и не заменять полное руководство.

## Требования к PDF

Пересобирайте `output/pdf/docs.pdf` из актуального `docs.md` только при выпуске новой версии приложения. В обычных задачах PDF не меняйте.

PDF должен:

- содержать тот же смысловой текст, таблицы и порядок разделов, что и `docs.md`;
- корректно отображать кириллицу, формулы и специальные символы;
- сохранять рабочие внутренние гиперссылки;
- не содержать обрезанного текста, наложений, пустых страниц и повреждённых символов;
- сохранять текст выделяемым и доступным для поиска;
- удерживать текст первого столбца каждой таблицы в пределах одной строки;
- иметь единообразные заголовки, поля, колонтитулы и номера страниц.

Отрисуйте все страницы PDF в изображения и просмотрите их перед выпуском. Дополните визуальную проверку программной: проверьте число страниц, ссылки, наличие ключевых исправлений и отсутствие запрещённых фрагментов.

## Проверка перед завершением задачи

Документация готова, если выполнены все применимые проверки:

1. Текст сверён с текущим интерфейсом, кодом и встроенными данными.
2. `docs.md` и README синхронизированы в пределах изменения.
3. Содержание и внутренние ссылки ведут к существующим разделам.
4. Все Markdown-таблицы имеют правильную структуру.
5. Изменённые фрагменты проверены ru-text, замечания обработаны.
6. `git diff --check` не сообщает об ошибках.
7. Тесты проекта запущены, если документация описывает изменённое поведение программы.
8. Итоговый diff содержит только файлы, относящиеся к задаче.

При выпуске новой версии дополнительно:

1. Полная вычитка `docs.md` через ru-text завершена, замечания обработаны.
2. PDF пересобран, программно проверен и просмотрен постранично.
3. Первый столбец каждой таблицы в PDF остаётся однострочным.

В отчёте о завершении перечислите изменённые файлы и выполненные проверки. Не заявляйте о вычитке, тестировании или визуальном контроле без фактического результата.
